# FS_PARSE_PLAN — 원문 XML에서 재무제표 본표 파싱 (fs_account 전 상장사 확장)

> **한 줄**: 이미 로컬에 있는 사업보고서 원문 27GB에서 재무제표 본표를 파싱해, `fs_account`를 55사 → 최대 2,590사로 넓힌다.
> 배경 원장: [../../integration/DECISIONS.md](../../integration/DECISIONS.md) **FN-025** (firm JSON 매출 오염 269사)
> 소관: `modules/report/` — 리더 소유. financial 모듈 코드는 건드리지 않는다.

## 1. 왜 하는가 (2026-08-11 실측으로 확정된 문제)

lite·EQS가 쓰는 13계정은 `firm_<t>.json`에서 오고, 그 원재료는 financial 모듈의 `eqs_v3_panels_2021_2025.json`이다. 그런데:

| 사실 | 실측 |
|---|---|
| firm JSON 매출이 오염된 기업 | **비금융·비지주 269사** (`\|영업이익\| > 매출`), 매출 급락후급반등 20사 |
| 원인 | financial `collector.py`가 `이자수익`을 조건 없이 revenue로 매핑 + **첫 값 우선**이라, DART 응답에서 이자수익 행이 먼저 오면 진짜 매출을 밀어냄 (FN-025) |
| 오염 사례 | 카카오 FY23 매출 0.19조(정답 7.557조) · **골든 한화에어로 FY25 0.22조**(정답 26.70조) |
| 재생성 가능 여부 | **불가** — `modules/financial/data/universe/`가 비어 있어 패널 파일이 로컬에 없다 |
| 우리 대안(`fs_account`) | **55사뿐** — `fs_enrich.py`가 DART API 재호출 방식이라 골든 클러스터에만 돌렸다 |

**그런데 원문은 이미 다 있다.**

| 자산 | 실측 (2026-08-11) |
|---|---|
| 원문 XML | `modules/report/data/raw_cache/` — **2,590사 · 12,090건 · 27GB** |
| `report_raw` | 2,590사, **5개년 보유 2,225사** |
| `report_section` | 428,420건 — 단 **주석만** 파싱됨(`III.3.연결주석`·`III.5.별도주석`·`II.사업의내용`) |
| 재무제표 본표 | **파싱 안 됨** — 그러나 XML 안에 그대로 있다 |

**결정적 확인**: 카카오 FY2023 원문(`raw_cache/035720/20240418000375.xml`, 8.6MB)에서
`구분 / 제29(당)기 / 제28(전)기 / 제27(전전)기 … 영업수익 7,557,001,757,272 …` 를 직접 확인했다.
→ **정답이 우리 파일 안에 있다. 재수집도, financial 모듈 수정 대기도 필요 없다.**

## 2. 설계

```
modules/report/data/raw_cache/<ticker>/<rcept_no>.xml   (입력 — 이미 있음)
        │
        ▼  fs_parse.py (신설)         ※ LLM 미사용, 규칙 파싱만 (D7)
   연결재무제표 본표 추출 → 계정 × (당기·전기·전전기)
        │
        ▼
   fs_account_xml  (신설 테이블 — 기존 fs_account를 오염시키지 않는다)
        │
        ▼  대조 검증 (55사 정답지)
   일치율 측정 → 임계 통과 시 fs_account로 승격/병합
```

### 왜 별도 테이블인가
기존 `fs_account` 55사는 **DART API 산출 = 정답지**다. 파서 결과를 같은 테이블에 섞으면 검증 기준이 사라진다.
파일럿 단계에서는 `fs_account_xml`에 쌓고, 일치율이 임계를 넘은 뒤에 병합 규칙을 정한다.

### 한 보고서에 3개년이 들어 있다
사업보고서 본표는 `당기 / 전기 / 전전기` 3열이다 → **FY25 보고서 1건으로 23·24·25**를 얻는다.
따라서 5개년을 채우는 데 보고서 2건(FY25 + FY22)이면 충분하고, 이는 **report_raw 5개년 미보유 365사의 커버리지도 끌어올린다**.

### 뽑을 계정 (galaxy/lite 13계정 + 골든이 쓰는 확장분)
`revenue · cogs · operating_income · net_income · operating_cashflow · investing_cashflow · financing_cashflow · total_assets · total_liabilities · total_equity · current_assets · current_liabilities · long_term_debt`
여력이 되면 골든이 쓰는 것(법인세·OCI·기초/기말현금·배당·자기주식)도 — 우선순위는 13계정.

### 규율
- **연결(CFS) 우선, 없으면 별도(OFS)** — 어느 쪽을 썼는지 행에 남긴다(`sj_div` 활용 또는 컬럼 추가)
- **계정명 우선순위를 명시한다** — `매출액/영업수익/수익(매출액)/매출` > `이자수익/수수료수익/보험수익`.
  FN-025의 재발 방지 조문: **조건 없는 별칭은 그 계정을 부수적으로 보고하는 회사에서 본래 값을 덮어쓴다.**
  first-wins로 두지 말고 **우선순위 정렬 후 최상위 1건**을 택할 것.
- **파생·합산 금지** — 원문에 합계 행이 없으면 만들지 않는다(미발견으로 기록)
- 출력 행마다 `rcept_no`를 남겨 추적 가능하게 (기존 fs_account 스키마와 동일)

## 7. P0 구조 노트 (2026-08-11 실측 — 55사 × 283 보고서 전수)

> 측정 대상: `fs_account` 정답지 55사가 보유한 `report_raw` 285건(파일 실재 283건). 눈으로 확인 + 전수 계측.

### 7.1 결정적 발견 — 본표 셀에 XBRL 태그가 그대로 있다

본표는 자유 서식 표가 아니라 **XBRL 태깅된 표**다. 셀 속성에 표준계정ID와 컨텍스트가 박혀 있다:

```xml
<TE ENG="Revenue" ...>영업수익</TE>
<TE ACODE="ifrs-full_Revenue"
    ACONTEXT="CFY2025dFY_..._ConsolidatedMember" ADECIMAL="0" ...>8,099,147,815,086</TE>
<TE ACODE="ifrs-full_Revenue" ACONTEXT="PFY2024dFY_..._ConsolidatedMember" ...>7,864,033,326,475</TE>
<TE ACODE="ifrs-full_Revenue" ACONTEXT="BPFY2023dFY_..._ConsolidatedMember" ...>7,554,821,329,554</TE>
```

`ACODE`는 **DART API의 `account_id`와 같은 값**이다(`ifrs-full_Revenue`·`dart_OperatingIncomeLoss`…).
→ FN-025의 재발 위험이 구조적으로 낮아진다: `ifrs-full_Revenue`와 `ifrs-full_RevenueFromInterest`는 **다른 ID**라 이름 별칭처럼 섞이지 않는다. 계정명은 2순위 폴백으로만 쓴다.

### 7.2 원문 형식 2종 — 경계는 FY2023

| 형식 | 대상 | 앵커 | 셀 | ACODE | 계정명 |
|---|---|---|---|---|---|
| **신형식** | FY2023~ (2024년 이후 제출) | `<TITLE>2-1. 연결 재무상태표</TITLE>` 류 | `<TE>` | FY24·25 **107/107 有**, FY23 **0/54 無** | 항상 |
| **구형식** | FY2021·22 | `<TABLE-GROUP ACLASS="{XBRL}BS">` 류 | `<TD><P>` | 셀에 없음 | 항상 |

- 신형식 본표 TITLE 검출 **161/161**(FY23+ 전량). 미검출 121건은 전부 FY22 이하 = 구형식.
- 구형식 ACLASS: 연결 `BS·IS2·IS3·EF·CF`, 별도는 `_S` 접미(`BS_S·IS_S2·IS_S3·EF_S·CF_S`). 표 이름은 캡션 표의 `<P USERMARK="F-12 B">연결 손익계산서</P>`.
- **FY2023 보고서는 신형식이지만 ACODE가 없다** — 계정명 매칭이 필수 경로다(ACODE 단독 설계는 FY23 전량을 잃는다).

### 7.3 연결/별도 구분

- 신형식: TITLE 그룹번호 — **`2-N` = 연결(CFS)**, **`4-N` = 별도(OFS)**. 표 이름에도 `연결` 접두.
- 구형식: ACLASS `_S` 접미가 별도.
- `ACONTEXT`에도 `_ConsolidatedMember`가 실려 있으나 별도 표에서의 표기 변형이 있어 **1순위 판정은 TITLE/ACLASS**로 한다.
- 정답지(`fs_enrich`)는 `fs_div=CFS` 우선·없으면 OFS라, 파서도 **연결 우선 → 없으면 별도**로 맞춘다.

### 7.4 3개년 열 배치 — 전수 동일

- 데이터 표는 **4열 고정**(계정명 + 당기 + 전기 + 전전기). 161/161 전량 4열.
- 캡션 표에 기수·기간이 3줄: `제 31 기 2025.01.01 부터 2025.12.31 까지` / `제 30 기 2024…` / `제 29 기 2023…`. 헤더 기수 3개 **161/161**.
- **당기 열의 연도 == `report_raw.fiscal_year` 161/161 일치** → 열→FY 매핑은 `[fy, fy-1, fy-2]`로 결정적이다.
- BS는 시점 표기(`제 31 기 2025.12.31 현재`), IS/CIS/CF는 기간 표기 — 어느 쪽이든 당기 열이 첫 열.

> ⚠️ **전전기 열은 재작성(restated) 값일 수 있다.** 카카오 FY2023 영업수익은 FY23 보고서 당기 **7,557,001,757,272**인데 FY25 보고서의 전전기 열은 **7,554,821,329,554**다(차 21.8억). 정답지(`fs_account`)는 각 연도 **자기 보고서의 당기**이므로, **당기 > 전기 > 전전기** 우선순위로 중복을 접어야 G1이 성립한다. 전기·전전기는 **자기 연도 보고서가 없을 때의 보충용**이다.

### 7.5 단위 — 3종, 스케일링 필수

IS/CIS 표 캡션 `(단위 : XXX)` 실측: **원 77 · 백만원 62 · 천원 22**.
정답지(DART API `thstrm_amount`)는 **원 단위**라, 파싱값에 `원=1 / 천원=1e3 / 백만원=1e6` 배율을 곱해야 한다. 단위는 **표(TABLE-GROUP)마다 따로** 읽는다 — 한 보고서 안에서 본표와 주석이 다른 단위를 쓴다.

### 7.6 음수 표기

괄호가 정본이다: `(478,201,170,293)` = 음수. `ANEGATED` 속성은 **신뢰할 수 없다**(괄호인데 `ANEGATED="N"`인 셀 실측). → **괄호·`△`·`▲`·선행 `-`** 를 음수로 읽고 `ANEGATED`는 무시한다.

| 키 | 실측된 계정명 변형 |
