## 0. 목표·비목표

**목표**: 관계가 하나도 없는 상장사 1,202사 중 ~1,011사(84%)를 채운다 — 강원랜드(자회사
전부 비상장)·케어젠(개인 대주주)처럼 데이터는 있는데 "노드는 상장사만" 원칙 때문에
비어 있는 화면을 해소. 노드 2,651 → ~27,700 (신규 비상장류 ~25,030 · 엣지 +~34,000).

**비목표 (이번 확대에서 안 하는 것)**:

  **등장 표면은 EgoView(이웃)와 팝오버뿐.**

- 5% 미만 지분·개인 소액주주 노드화 없음 — K-IFRS 임계값 유지(케어젠→아모레퍼시픽
  2,941주 같은 단순투자는 여전히 제외).

## 1. 노드 유형 체계 (범례 = NODE TYPOLOGY)

리더 지시 "개인주주·비상장법인 등등 나누어서" — **4종 + 상장(기존)**:

| kind | 한글 라벨 | 판별 (실측 검증된 휴리스틱 승격) | 규모 감각치 |
|---|---|---|---|
| `listed` | 상장사 (기존) | CompanyRegistry | 2,651 |
| `private_corp` | 비상장법인 | 법인격 표지(㈜·주식회사·Ltd·Inc·공사·은행…) 보유, 아래 셋 아님 | 최다 (~2만) |
| `person` | 개인 | hyslrSttus relate(본인·친인척·자녀…) 또는 무표지 2~4자 한글 | hyslr에서만 |
| `coop_fund` | 조합·펀드 | 조합·펀드·투자회사·신탁·공제 어휘 | 수백 (공제조합 허브) |
| `public_org` | 공공기관 | 공단·공사·진흥원·연구원·재단(공익) 어휘 | 소수 (한국광해광업공단류) |

- 해외법인은 별도 kind로 두지 않는다(범례 5칸 초과 = 밀도 위반). `private_corp`에 포함,
  라벨이 라틴문자라 화면에서 자연 구분.
- 분류기는 조사 스크립트(`unlisted_impact.py`)의 잡음 게이트·판별 로직을 **프로덕션 승격** +
  실공시 fixture 테스트. 오분류는 CPA 스팟체크(G-C)로 검증.

## 2. 신원 체계 — 이번 확대의 최대 리스크 지점

비상장은 corp_code·ticker가 없다 — **공시 원문의 문자열이 신원의 전부**다(FN-013
"이름 정확 일치는 신원 증명이 아니다"가 정면으로 걸리는 지점).

- **uid**: `u_` + sha1(normalize_company_name(name))[:12]. 결정적·멱등.
- **표기 통합**: 실측상 25,030 표기 → 정규화 22,728 키(2,032 키가 복수 표기 — `(주)시큐아이`
  / `㈜시큐아이`, 개행 섞인 외국명). name_display는 최다 빈도 표기 채택.
- **상장사명과 정규화 충돌 0건 실측** — 허위 상장 링킹 위험은 이 후보군엔 없음(재확인 게이트 유지).
- **⚠️ 개인 노드는 전역 병합 금지 (제안 — 열린 결정 §8-1)**: '김철수'가 두 회사 대주주면
  동일인 보장이 없다. 개인 uid = `p_` + sha1(정규화이름 + **앵커 corp_code**)[:12] —
  즉 개인은 **앵커-로컬 노드**(회사마다 별개, 화면상 그 회사 ego에만 등장)로 시작한다.
  법인은 전역 병합(사업자 단위 실체가 있고 표기 충돌 실측이 관리 가능 범위).
- **방어 5층 적용**: L1(영문 2~5자 약칭)은 비상장 노드화에도 적용 — 약칭은 노드로 만들지
  않고 LinkFailQueue 유지(HMA를 'HMA'라는 노드로 만들면 오염이 노드로 승격될 뿐).
  L2(쌍 블록리스트)·L5(큐) 유지. L3·L4(지분율)는 기존 그대로.

## 3. 데이터 모델

```
UnlistedEntity (신규 테이블 — modules/relation/storage/models.py)
  uid TEXT PK            -- u_/p_ 프리픽스 합성키 (§2)
  name_norm TEXT         -- 정규화 키 (법인은 UNIQUE, 개인은 앵커 스코프)
  name_display TEXT      -- 화면 표기 (최다 빈도)
  kind TEXT              -- private_corp / person / coop_fund / public_org
  anchor_corp TEXT NULL  -- person 전용: 스코프 앵커 corp_code
  first_seen TEXT        -- 최초 등장 rcept_no·source (provenance)
  status TEXT            -- active (prune은 생산자 소관 조문 준수)
```

- **RelationLocal·ValueChainEdge는 스키마 불변** — source/target 컬럼에 uid를 그대로 넣는다
  (6자리 ticker와 `u_`/`p_` 프리픽스로 형태 충돌 없음). 마이그레이션 1회(테이블 추가만).
- **prune 소유권 (조문 준수)**: UnlistedEntity와 그 엣지의 생산자는 각 파서(filters=지분,
  related_party=주석). 각자 자기 source_type 스코프만 정리 — dart_filing 소실 사고 재발 방지.

## 5. Export·계약 변경

- **ego 이웃 스키마 확장** (universe/export.py):
  `{uid, n, kind, type, detail, dir, ...}` — 상장 이웃은 기존 `{t, n, s, tier, ...}` 불변.
  **`t`(티커) 필드가 없는 이웃 = 비상장** — adapter가 kind로 렌더 분기.
- **companies_index는 불변(2,651 상장만) — 비상장은 ego-로컬 자급 (제안 — 열린 결정 §8-2)**:
  비상장 이웃 객체가 이름·kind를 스스로 들고 있어 인덱스 조회가 필요 없다.
  전역 인덱스에 25K를 넣으면 companies_index ~300KB → ~2.5MB (초기 로드 부담) + V-3 무결성
  규칙 전면 개정 필요. ego-로컬이면 V-3 규칙은 "「t 있는 이웃」은 index에 존재해야 한다"로
  한 줄 수정.
- rl-string(universe.json) 불변 — named400 상호 관계만 담는 계약이라 비상장 비관여.
- 파일 크기 게이트: ego 총량(현 ~15MB 추정) 재실측 — 이웃 급증 시 상위 컷(§6)이 흡수하는지 확인.
